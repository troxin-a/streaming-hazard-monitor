# streaming-hazard-monitor

Пет-проект: система мониторинга опасности на предприятиях. Датчики (газ, дым, температура и другие) стоят в зданиях и присылают показания, система их принимает и хранит.

Цель проекта — на практике разобраться с Kafka. Проект развивается по шагам: сначала самое простое решение, потом становится видно, чего ему не хватает, и после этого добавляется технология, которая это закрывает.

## Что уже есть

- `api` — пользовательский API: вход по JWT, компании, здания, устройства, пользователи, выпуск и отзыв api-ключа устройства.
- `receiver` — приём показаний от датчиков: `POST /receiver/telemetry/`, ключ устройства в заголовке `X-API-Key`, в теле только `value`. Показание сразу пишется в Postgres.
- `frontend` — веб-интерфейс на React.
- Нагрузочный тест на k6.

Kafka, обработки порогов и алертов пока нет.

## Запуск

Нужны Docker и Docker Compose.

1. Создать файл с настройками и поправить в нём значения:

   ```bash
   cp .env_example .env
   ```

2. Поднять сервисы:

   ```bash
   docker compose up -d --build
   ```

3. Применить миграции:

   ```bash
   docker compose exec api alembic upgrade head
   ```

После этого доступны:

- API и его документация: http://localhost:8000/api/docs/
- приём показаний и его документация: http://localhost:8001/receiver/docs/
- фронт: http://localhost:5173
- Postgres: порт 5433

## Тесты

Тестам нужен запущенный Postgres: на время прогона они создают отдельную базу и удаляют её в конце.

```bash
docker compose exec api pytest
```

Только один раздел:

```bash
docker compose exec api pytest tests/telemetry
```

## Нагрузочный тест

Тест написан на [k6](https://k6.io). Как установить k6 на свою систему, описано в [документации](https://grafana.com/docs/k6/latest/set-up/install-k6/). Проверить, что он установлен:

```bash
k6 version
```

Скрипты запускаются с машины, а не из контейнера, поэтому нужно виртуальное окружение с зависимостями из `requirements.txt` и `POSTGRES_HOST=localhost` в `.env`.

1. Создать тестовые устройства. Скрипт заводит компанию, здание и 1700 устройств, а их ключи пишет в `scripts/k6-keys.json`:

   ```bash
   python -m scripts.create_load_devices
   ```

2. Запустить тест. `RATE` — сколько запросов в секунду отправлять, тест идёт одну минуту:

   ```bash
   k6 run -e RATE=750 scripts/k6-test.js
   ```

3. После замеров удалить тестовые устройства и файл с ключами:

   ```bash
   python -m scripts.remove_load_devices
   ```

На что смотреть в итоге:

- `http_req_failed` — доля запросов без ответа `201`;
- `http_req_duration` — время ответа;
- `dropped_iterations` — если строка есть, k6 не смог выдать заданную частоту.

Между запусками лучше перезапускать receiver, иначе очередь от прошлого прогона попадёт в следующий:

```bash
docker compose restart receiver
```

### Результаты

Замер от 9 октября 2026. Receiver пишет каждое показание в Postgres прямо в обработчике запроса. Менялось только число воркеров uvicorn.

| Воркеров | Держит, запросов в секунду | Ломается на | Медиана / p95 | CPU receiver | CPU базы | Во что упирается |
|---|---|---|---|---|---|---|
| 1 | 700 | 750 | 4 / 8 мс | 91% | 25% | процессор receiver |
| 2 | 1200 | 1300 | 7 / 24 мс | 178% | 42% | процессор receiver |
| 4 | 1900 | 2100 | 9 / 30 мс | 299% | 60% | |
| 8 | 2800 | 3100 | 12 / 44 мс | 560% | 103% | запись на диск в Postgres |

Время ответа и загрузка процессора сняты на той частоте, которую сервис держит. 100% CPU — это одно ядро.

Как мерили:

- прогон идёт минуту, датчик ждёт ответа не дольше секунды;
- «держит» значит, что отказов меньше 0,1% и k6 отправил все запросы;
- перед каждым прогоном receiver перезапускается, после — тестовые показания удаляются из базы;
- граница найдена с точностью около 10%, по одному прогону на частоту;
- машина с 16 ядрами, k6 запущен на ней же и отнимает процессор у сервисов;
- пул соединений с базой — 10 на воркер.

Что видно:

- один воркер упирается в процессор: один процесс Python занимает одно ядро;
- каждый следующий воркер даёт меньше предыдущего: восемь воркеров принимают в четыре раза больше одного, а не в восемь;
- на восьми воркерах запас по процессору у receiver ещё есть, а соединения с базой стоят в очереди на запись журнала на диск, потому что каждое показание сохраняется отдельной транзакцией.

Это числа для сравнения «до и после» на одной и той же машине, а не обещание производительности.

# streaming-hazard-monitor

Пет-проект: система мониторинга опасности на предприятиях. Датчики (газ, дым, температура и другие) стоят в зданиях и присылают показания, система их принимает и хранит.

Цель проекта — на практике разобраться с Kafka. Проект развивается по шагам: сначала самое простое решение, потом становится видно, чего ему не хватает, и после этого добавляется технология, которая это закрывает.

## Что уже есть

- `api` — пользовательский API: вход по JWT, компании, здания, устройства, пользователи, выпуск и отзыв api-ключа устройства.
- `receiver` — приём показаний от датчиков: `POST /receiver/telemetry/`, ключ устройства в заголовке `X-API-Key`, в теле только `value`. Показание отправляется в топик Kafka `sensor-readings`.
- `detector` — читатель топика: сравнивает показание с порогами датчика и при смене уровня опасности пишет алерт в Postgres. Сами показания в базу не пишутся, они остаются в Kafka.
- `frontend` — веб-интерфейс на React.
- Нагрузочный тест на k6.

Алерты пока видны только в базе: эндпоинтов и экрана для них нет.

## Запуск

Нужны Docker и Docker Compose.

1. Создать файл с настройками и поправить в нём значения:

   ```bash
   cp .env_example .env
   ```

2. Поднять сервисы:

   ```bash
   docker compose up -d --build
   ```

3. Применить миграции:

   ```bash
   docker compose exec api alembic upgrade head
   ```

После этого доступны:

- API и его документация: http://localhost:8000/api/docs/
- приём показаний и его документация: http://localhost:8001/receiver/docs/
- фронт: http://localhost:5173
- Postgres: порт 5433

## Тесты

Тестам нужен запущенный Postgres: на время прогона они создают отдельную базу и удаляют её в конце.

```bash
docker compose exec api pytest
```

Только один раздел:

```bash
docker compose exec api pytest tests/telemetry
```

## Нагрузочный тест

Тест написан на [k6](https://k6.io). Как установить k6 на свою систему, описано в [документации](https://grafana.com/docs/k6/latest/set-up/install-k6/). Проверить, что он установлен:

```bash
k6 version
```

Скрипты запускаются с машины, а не из контейнера, поэтому нужно виртуальное окружение с зависимостями из `requirements.txt` и `POSTGRES_HOST=localhost` в `.env`.

Каждый тестовый датчик шлёт одно показание в секунду, поэтому число запросов в секунду равно числу датчиков, которые шлют.

1. Создать тестовые устройства под самую большую частоту, которую собираетесь проверять. Скрипт заводит компанию, здание и устройства, а их ключи пишет в `scripts/k6-keys.json`:

   ```bash
   python -m scripts.create_load_devices --count 2000
   ```

2. Перезапустить receiver и detector: устройства и пороги они загружают при старте.

   ```bash
   docker compose restart receiver detector
   ```

3. Запустить тест, он идёт одну минуту. `RATE` — сколько датчиков шлют показания, то есть сколько запросов в секунду; без `RATE` шлют все созданные:

   ```bash
   k6 run -e RATE=750 scripts/k6-test.js
   ```

   С `CHATTER=1` значения шумят вокруг порога тревоги: примерно каждое второе показание оказывается по другую сторону порога. Без него все датчики остаются в норме:

   ```bash
   k6 run -e RATE=750 -e CHATTER=1 scripts/k6-test.js
   ```

   Прогоны с `CHATTER=1` сравнимы, только если перед каждым перезапустить detector: он держит уровни датчиков в памяти, и датчики, поднятые прошлым прогоном, в следующем остаются на уровне.

4. После замеров удалить тестовые устройства, их алерты и файл с ключами:

   ```bash
   python -m scripts.remove_load_devices
   ```

На что смотреть в итоге k6:

- `http_req_failed` — доля запросов без ответа `202`;
- `http_req_duration` — время ответа;
- `dropped_iterations` — если строка есть, k6 не смог выдать заданную частоту.

Успевает ли detector за потоком, показывает колонка `LAG`: сколько сообщений в каждой партиции он ещё не обработал.

```bash
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group threshold-detector
```

Сколько алертов записано:

```bash
docker compose exec db sh -c 'psql -p 5433 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*) from alerts"'
```

#### Шаг 1. Запись в Postgres

Замер от 9 октября 2026. Receiver пишет каждое показание в Postgres прямо в обработчике запроса. Менялось только число воркеров uvicorn.

| Воркеров | Держит, запросов в секунду | Ломается на | Медиана / p95 | CPU receiver | CPU базы | Во что упирается |
|---|---|---|---|---|---|---|
| 1 | 700 | 750 | 4 / 8 мс | 91% | 25% | процессор receiver |
| 2 | 1200 | 1300 | 7 / 24 мс | 178% | 42% | процессор receiver |
| 4 | 1900 | 2100 | 9 / 30 мс | 299% | 60% | |
| 8 | 2800 | 3100 | 12 / 44 мс | 560% | 103% | запись на диск в Postgres |

Время ответа и загрузка процессора сняты на той частоте, которую сервис держит. 100% CPU — это одно ядро.

Как мерили:

- прогон идёт минуту, датчик ждёт ответа не дольше секунды;
- «держит» значит, что отказов меньше 0,1% и k6 отправил все запросы;
- перед каждым прогоном receiver перезапускается, после — тестовые показания удаляются из базы;
- граница найдена с точностью около 10%, по одному прогону на частоту;
- машина с 16 ядрами, k6 запущен на ней же и отнимает процессор у сервисов;
- пул соединений с базой — 10 на воркер.

Что видно:

- один воркер упирается в процессор: один процесс Python занимает одно ядро;
- каждый следующий воркер даёт меньше предыдущего: восемь воркеров принимают в четыре раза больше одного, а не в восемь;
- на восьми воркерах запас по процессору у receiver ещё есть, а соединения с базой стоят в очереди на запись журнала на диск, потому что каждое показание сохраняется отдельной транзакцией.

#### Шаг 2. Отправка в Kafka

Замер от 10 октября 2026. Receiver больше не пишет в базу: он находит устройство по ключу и отправляет показание в топик `sensor-readings`, дожидаясь подтверждения от брокера. Условия те же, что в шаге 1.

| Воркеров | Держит | Ломается на | Медиана / p95 | CPU receiver | CPU базы | CPU Kafka |
|---|---|---|---|---|---|---|
| 1 | 850 | 900 | 1 / 3 мс | 92% | 10% | 25% |
| 8 | 4200 | 4450 | 26 / 199 мс | 608% | 63% | 50% |

Что видно:

- один воркер по-прежнему упирается в процессор, прирост около 20%;
- на восьми воркерах прирост 50%: запись журнала Postgres больше не мешает, база только читает;
- на 4200 хвост уже длинный, это край.

#### Шаг 3. Без журнала запросов

Uvicorn на каждый запрос пишет строку в консоль. Замер с флагом `--no-access-log`, остальное как в шаге 2.

| Воркеров | Держит | Ломается на | Медиана / p95 | CPU receiver | CPU базы |
|---|---|---|---|---|---|
| 1 | 1000 | 1100 | 3 / 47 мс | 101% | 14% |
| 8 | 3950 | 4200 (0,18% отказов) | 17 / 73 мс | 497% | 55% |

Что видно:

- одному воркеру журнал стоил 15–20% пропускной способности;
- на восьми воркерах предел не изменился: 3950 и 4200 из шага 2 неразличимы при точности 10%. Процессор и время ответа стали лучше, но ограничивает там что-то другое;
- что именно ограничивает восемь воркеров, не установлено: они заняты на две трети, база — на половину ядра из-за поиска устройства на каждый запрос.

#### Шаг 4. Устройства в памяти

Замер от 10 октября 2026. Раньше receiver на каждое показание искал устройство по ключу запросом в Postgres. Теперь он при старте загружает словарь «хеш ключа → устройство» и ищет в нём. В базу на пути запроса он больше не ходит. Остальное как в шаге 3.

| Воркеров | Держит | Ломается на | Медиана / p95 | CPU receiver | CPU базы | CPU Kafka |
|---|---|---|---|---|---|---|
| 1 | 2750 | 2900 | 2 / 160 мс | 106% | 1% | 13% |
| 8 | 8800 | граница не найдена | 16 / 99 мс | 357% | 2% | 15% |

Для сравнения, один воркер на 1000 запросов в секунду — на частоте, которая в шаге 3 была пределом:

| | Поиск в базе | Поиск в памяти |
|---|---|---|
| Медиана / p95 | 3 / 47 мс | 0,7 / 1,2 мс |
| CPU receiver | 101% | 50% |

Что видно:

- поиск устройства в базе занимал больше половины работы воркера: без него один воркер держит почти втрое больше;
- один воркер по-прежнему упирается в свой процессор, только намного позже;
- на восьми воркерах предел не найден. Прогон на 9750 формально не прошёл: 1218 таймаутов из 585 тысяч запросов, это 0,2% при пороге 0,1%. Но все они случились в первые две секунды после перезапуска receiver, когда k6 разом открывает тысячи соединений. Остальные 58 секунд прошли без единого отказа. Это прогрев, а не перегрузка;
- receiver на 8800 загружен меньше чем наполовину (357% из 800%), база и Kafka почти свободны. Выше этих частот, скорее всего, первым кончится генератор нагрузки: k6 работает на той же машине. Его загрузка не измерялась.

Оговорки:

- на 2750 один воркер работает на самом краю: медиана 2 мс, но p95 уже 160 мс. Запас виден на 2450, где p95 равен 5 мс;
- словарь загружается один раз при старте и не обновляется. Устройство, которому выпустили ключ после старта, получает `401` до перезапуска, а удалённое устройство продолжает приниматься. Это известное ограничение текущего шага.

Про обвал за пределом. Когда ответы выходят за секунду, k6 закрывает соединение и открывает новое. При тысячах таких соединений в секунду на машине кончаются свободные порты, и до сервера доходит малая часть нагрузки. Поэтому сразу за границей отказов становится 90% и больше: это свойство генератора на той же машине, а не только сервера.

#### Шаг 5. Читатель топика и дребезг

Замер от 11 октября 2026. Появился detector: он читает `sensor-readings`, сравнивает показание с порогами датчика и, когда уровень опасности датчика меняется, закрывает прежний алерт и открывает новый. Пороги и последний уровень каждого датчика он держит в памяти, в базу ходит только при смене уровня. Каждая смена — отдельная транзакция.

Изменился и сам тест: теперь каждый датчик шлёт ровно одно показание в секунду, а значение можно сделать шумным вокруг порога. Шум на всех датчиках сразу — самый тяжёлый режим для читателя топика: уровень меняется примерно на каждом втором показании.

Откуда дребезг. Это не наблюдение за настоящими датчиками, а смоделированный худший случай. У любого датчика есть шум измерения, и когда значение держится у порога (концентрация газа медленно растёт или стоит на границе), правило «уровень по одному показанию» заставляет датчик то входить в тревогу, то выходить из неё. Режим `CHATTER=1` доводит это до предела: у всех датчиков сразу значение стоит ровно на пороге, как если бы общая причина (например, выключенная вентиляция) подняла концентрацию во всём здании, а датчики были одинаково шумными.

Как устроен режим. Все тестовые датчики — датчики CO, порог уровня 1 у них 20 ppm. С `CHATTER=1` k6 шлёт значение 20 плюс случайный шум от −1 до +1, равномерно. Показание выше 20 относится к уровню 1, остальные — норма, так что каждое показание с вероятностью 1/2 оказывается по другую сторону порога от предыдущего.

Откуда 30 500. За минуту 2000 датчиков присылают 120 000 показаний. Примерно половина из них меняет уровень датчика — это около 60 000 смен. Половина смен — вверх, из нормы в уровень 1, и каждая такая смена открывает новый алерт; смена вниз только закрывает открытый. Выходит около 30 000 строк в `alerts`, замер дал 30 500.

Прогон: 2000 датчиков, 2000 запросов в секунду, одна минута, один экземпляр detector'а, три партиции.

| Режим | Отставание в конце минуты | Строк в `alerts` |
|---|---|---|
| все датчики в норме | не растёт | новых не появляется |
| значения шумят вокруг порога | около 27 000 в каждой партиции, всего около 81 000 из 120 000 сообщений | 30 500 |

Что видно:

- без смен уровня detector справляется с потоком: чтение из Kafka и сравнение с порогами в памяти дёшевы;
- с шумом он успевает обработать только треть сообщений. Упирается он в запись: по расчёту выходит около 325 смен уровня в секунду, по одной транзакции на каждую;
- приём от этого не страдает: receiver отвечает датчикам как раньше, а необработанные показания ждут в топике. Detector догоняет поток после конца прогона;
- 30 500 строк за минуту — это мусор: датчик, значение которого колеблется на единицу вокруг порога, не попадает в тревогу и не выходит из неё по тридцать раз в минуту.

Отсюда две отдельные задачи: detector не успевает писать, и в таблице появляются лишние алерты.

#### Шаг 6. Запись пачками

Замер от 11 октября 2026. Detector берёт из Kafka до ста сообщений за раз, собирает из них все смены уровня и пишет их одной транзакцией: одним запросом закрывает прежние алерты и одним открывает новые. Позицию в топике он фиксирует после того, как пачка записана в базу. Остальное как в шаге 5.

| | Транзакция на каждую смену | Запись пачками |
|---|---|---|
| Отставание на партицию, шум вокруг порога | около 27 000 в конце минуты | не больше 65 за весь прогон, временами около 5 |

Что видно:

- отставание исчезло при том же числе смен уровня: дорогой была не сама запись строки, а отдельная транзакция на каждую;
- лишние алерты никуда не делись: смен уровня столько же, пачки только удешевили их запись. Это следующая задача: уровень датчика надо определять не по одному показанию, а по нескольким последним.

#### Шаг 7. Серии показаний подряд

Замер от 15 октября 2026. Уровень датчика меняется не по одному показанию, а по серии. Чтобы подняться, нужно 5 показаний подряд выше текущего уровня; чтобы опуститься — 15 подряд ниже. Одно показание текущего уровня или в другую сторону обрывает серию, и счёт начинается заново. Когда серия набралась, датчик встаёт на уровень её последнего показания. Остальное как в шаге 6.

Длины разные намеренно. Подъём короткий, чтобы настоящая тревога приходила через 4 секунды. Спуск длинный, чтобы шум у порога не сбрасывал уровень: при значении, которое колеблется на единицу вокруг порога, 15 показаний подряд ниже почти не случаются. Длины выбраны моделированием до прогона и вынесены в переменные окружения `DETECTOR_RISE_COUNT` и `DETECTOR_FALL_COUNT`.

На датчик хранится один счётчик со знаком: плюс — сколько показаний подряд выше уровня, минус — сколько ниже. Окно из последних показаний не нужно.

| | Запись пачками | Пачки и серии |
|---|---|---|
| Строк в `alerts`, шум вокруг порога | 30 500 | 1242 и 1288 (два прогона) |
| Отставание на партицию | не больше 65 | не больше 17 |

Что видно:

- строк стало примерно в 24 раза меньше. Оставшиеся — это датчики, которые за минуту успели набрать пять показаний подряд выше порога и встали на уровень 1. Обратно они не опускаются, поэтому в следующую минуту новых строк почти нет. Моделирование предсказывало 1220;
- отставание тоже упало: смен уровня почти не стало, писать нечего;
- detector перед прогоном нужно перезапускать. Без перезапуска он помнит, какие датчики уже подняты, и прогоны подряд дали 644, 228, 75 и 23 строки: каждый следующий поднимал только тех, кто ещё не поднялся.

Это числа для сравнения «до и после» на одной и той же машине, а не обещание производительности.

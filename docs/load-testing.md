# Нагрузочные тесты

Запуск нагрузочного теста и результаты замеров. Сводка - в [README](../README.md#результаты).

## Запуск

Тест написан на [k6](https://k6.io). Установка - в [документации](https://grafana.com/docs/k6/latest/set-up/install-k6/). Проверить, что он установлен:

```bash
k6 version
```

Скрипты запускаются с машины, а не из контейнера, поэтому нужно виртуальное окружение с зависимостями из `requirements.txt` и `POSTGRES_HOST=localhost` в `.env`.

Каждый тестовый датчик шлет одно показание в секунду, поэтому число запросов в секунду равно числу датчиков, которые шлют.

1. Создать тестовые устройства под самую большую частоту, которую собираетесь проверять. Скрипт заводит компанию, здание и устройства, а их ключи пишет в `scripts/k6-keys.json`:

   ```bash
   python -m scripts.create_load_devices --count 2000
   ```

2. Перезапустить receiver и detector: устройства и пороги они загружают при старте.

   ```bash
   docker compose restart receiver detector
   ```

3. Запустить тест, он идет одну минуту. `RATE` - число датчиков, которые шлют показания, оно же RPS. Без `RATE` шлют все созданные:

   ```bash
   k6 run -e RATE=750 scripts/k6-test.js
   ```

   С `CHATTER=1` значения шумят вокруг порога тревоги: примерно каждое второе показание оказывается по другую сторону порога. Без него все датчики остаются в норме:

   ```bash
   k6 run -e RATE=750 -e CHATTER=1 scripts/k6-test.js
   ```

   Прогоны с `CHATTER=1` сравнимы, только если перед каждым перезапустить detector: он держит уровни датчиков в памяти, и датчики, поднятые прошлым прогоном, в следующем остаются на уровне.

4. После замеров удалить тестовые устройства, их алерты и файл с ключами:

   ```bash
   python -m scripts.remove_load_devices
   ```

В итоге k6 нужны три строки:

- `http_req_failed` - доля запросов без ответа `202`
- `http_req_duration` - время ответа, из нее берутся медиана и p95. Медиана 1 мс: половина запросов получила ответ быстрее 1 мс. p95 74 мс: 95% запросов быстрее 74 мс
- `dropped_iterations` - если она есть, k6 не смог выдать заданную частоту

RPS (requests per second) - запросов в секунду.

Отставание detectorа показывает колонка `LAG` - число необработанных сообщений в каждой партиции.

```bash
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group threshold-detector
```

Число записанных алертов:

```bash
docker compose exec db sh -c 'psql -p 5433 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*) from alerts"'
```

## Условия замеров

Условия одинаковые для всех замеров, между прогонами меняется что-то одно.

- Прогон идет одну минуту на одной частоте. Каждый тестовый датчик шлет одно показание в секунду, поэтому частота равна числу датчиков, которые шлют.
- Датчик ждет ответа не больше секунды, дольше - это отказ.
- Частота считается выдержанной, если отказов меньше 0,1% и в итоге k6 нет `dropped_iterations`.
- Перед каждым прогоном receiver перезапускается.
- Перед прогонами с шумом у порога перезапускается и detector, чтобы уровни датчиков начинались с нормы.
- Тестовые датчики создаются до запуска receiverа и detectorа.
- После серии замеров удаляются топики `sensor-readings` и `device-levels`, чтобы данные не копились на диске. После этого перезапускается `api`, иначе он не читает пересозданный `device-levels`.
- Все работает на одной машине (Ryzen 7 8700G, 8 ядер / 16 потоков), k6 запущен там же и забирает часть процессора у сервисов.

## Замеры по шагам

Предел receiverа в RPS после каждого изменения. Между соседними строками менялось что-то одно.

| Receiver | 1 воркер | 8 воркеров |
|---|---|---|
| пишет показание в Postgres | 700 | ~2800 |
| отправляет показание в Kafka | 1000 | ~3950 |
| ищет устройство по ключу в словаре в памяти | 2750 | не меньше 8800 |

Эти замеры сделаны первой версией теста: он слал от 1700 датчиков при любой частоте и выбирал датчик случайно.

Прогон: 2000 датчиков с шумом вокруг порога, одна минута, один экземпляр detectorа.

| Detector | LAG в конце прогона | Строк в `alerts` |
|---|---|---|
| пишет каждую смену уровня отдельной транзакцией | ~27 000 | ~30 500 |
| пишет смены уровня пачками | ~65 | ~30 500 |
| меняет уровень только после серии показаний подряд | ~17 | ~1250 |

### Шаг 1. Запись в Postgres

Receiver пишет каждое показание в Postgres прямо в обработчике запроса. Менялось только число воркеров uvicorn.

| Воркеров | RPS | Медиана / p95 | CPU receiver | CPU базы |
|---|---|---|---|---|
| 1 | 700 | 4 / 8 мс | 91% | 25% |
| 2 | 1200 | 7 / 24 мс | 178% | 42% |
| 4 | 1900 | 9 / 30 мс | 299% | 60% |
| 8 | 2800 | 12 / 44 мс | 560% | 103% |

Время ответа и загрузка процессора сняты на той частоте, которую сервис держит. 100% CPU - это один поток процессора.

Пул соединений с базой ограничен 10 соединениями на воркер, без временных (`pool_size=10, max_overflow=0`). По умолчанию SQLAlchemy держит до 15 соединений на процесс: 5 постоянных и до 10 временных. У восьми воркеров это до 120 соединений, а Postgres по умолчанию принимает 100. Уже на 2000 запросов в секунду receiver отдавал `500` с `TooManyConnectionsError`. С пулом 10 восемь воркеров открывают не больше 80 соединений, и ошибка ушла.

Новые воркеры помогают слабо: восемь держат только в четыре раза больше одного, дальше упирается запись в Postgres.

### Шаг 2. Отправка в Kafka

Receiver больше не пишет в базу: он находит устройство по ключу и отправляет показание в топик `sensor-readings`, дожидаясь подтверждения от брокера.

| Воркеров | RPS | Медиана / p95 | CPU receiver | CPU базы |
|---|---|---|---|---|
| 1 | 1000 | 3 / 47 мс | 101% | 14% |
| 8 | 3950 | 17 / 73 мс | 497% | 55% |

Один воркер по-прежнему упирается в процессор. На восьми запись в Postgres больше не мешает. Но receiver все еще ищет устройство по ключу запросом в базу на каждое показание.

### Шаг 3. Устройства в памяти

При старте receiver загружает словарь {хеш ключа: устройство} и ищет в нем. В базу на пути запроса он больше не ходит.

| Воркеров | RPS | Не выдерживает | Медиана / p95 | CPU receiver | CPU базы | CPU Kafka |
|---|---|---|---|---|---|---|
| 1 | 2750 | 2900 | 1 / 74 мс | 85% | 0% | 46% |
| 8 | 8800 | граница не найдена | 16 / 99 мс | 357% | 2% | 15% |

Поиск устройства в базе занимал больше половины работы воркера: на 1000 RPS с поиском в базе воркер был занят на 101%, с поиском в памяти - на 50%. Без него один воркер держит почти втрое больше.

На восьми воркерах предел не найден. Receiver на 8800 загружен меньше чем наполовину (357% из 800%), база и Kafka почти свободны.

Ключи меняются редко, а показание приходит от каждого датчика раз в секунду, так что читать базу на каждый запрос незачем.

Сначала словарь загружался только при старте, и новое устройство получало `401` до перезапуска receiverа. Потом я сделал перезагрузку из базы раз в минуту, и новый или удаленный ключ начинает действовать с задержкой до минуты.

Память я прикинул по объему данных. На устройство приходится хеш ключа из 64 символов (64 байта) и UUID (16 байт), всего 80 байт. На миллион устройств это 80 МБ на процесс и 640 МБ на восемь воркеров, у каждого своя копия. При перезагрузке новый словарь собирается, пока старый еще работает, так что на это время память под словарь удваивается.

### Шаг 4. Читатель топика и дребезг

Появился detector. Он читает показания из Kafka, сравнивает их с порогами и при смене уровня датчика пишет алерт в Postgres, каждую смену отдельной транзакцией. Пороги и текущие уровни датчиков он держит в памяти.

В тесте есть режим `CHATTER=1`: порог тестовых датчиков 20, а k6 шлет 20 плюс-минус 1. Уровень датчика меняется примерно на каждом втором показании. Это худший случай: все датчики сразу шумят у порога.

За минуту 2000 датчиков присылают 120 000 показаний. Половина из них меняет уровень, половина смен идет вверх и открывает алерт ~30 500 строк в `alerts`.

Прогон: 2000 датчиков, по одному показанию в секунду, одна минута, один detector.

| Режим | LAG в конце прогона | Строк в `alerts` |
|---|---|---|
| все датчики в норме (без `CHATTER`) | не растет | новых не появляется |
| значения шумят вокруг порога (`CHATTER=1`) | ~27 000 в каждой партиции, всего ~81 000 из 120 000 сообщений | ~30 500 |

В норме detector успевает. С шумом он обрабатывает только треть показаний: упирается в запись в базу. Receiver при этом отвечает датчикам как обычно, показания ждут в Kafka.

30 500 строк за минуту - эт плохо: датчик скачет через порог туда и обратно. Появились две задачи: detector не успевает писать, и в базе лишние алерты.

### Шаг 5. Запись пачками

Detector берет из Kafka до ста сообщений за раз, собирает из них все смены уровня и пишет их одной транзакцией: одним запросом закрывает прежние алерты и одним открывает новые. Позицию в топике он фиксирует после того, как пачка записана в базу.

| Запись | LAG при включенном шуме |
|---|---|
| транзакция на каждую смену | ~27 000 |
| пачками | ~5-65 |

Смен уровня столько же, а отставания почти нет. Значит, дорого обходилась отдельная транзакция на каждую смену. Лишних алертов столько же, пачки только удешевили их запись. С ними поможет только одно: определять уровень по нескольким последним показаниям.

### Шаг 6. Серии показаний подряд

Уровень датчика меняется не по одному показанию, а по серии. Чтобы подняться, нужно 5 показаний подряд выше текущего уровня, чтобы опуститься - 15 подряд ниже. Одно показание текущего уровня или в другую сторону обрывает серию, и счет начинается заново. Когда серия набралась, датчик встает на уровень ее последнего показания.

Подъем короткий, чтобы настоящая тревога приходила через 4 секунды. Спуск длинный, чтобы шум у порога не сбрасывал уровень: при значении, которое колеблется на единицу вокруг порога, 15 показаний подряд ниже почти не случаются. Длины вынесены в переменные окружения `DETECTOR_RISE_COUNT` и `DETECTOR_FALL_COUNT`.

На датчик хранится один счетчик со знаком: плюс - число показаний подряд выше уровня, минус - ниже.

| Запись | LAG при включенном шуме | Строк в `alerts` при включенном шуме |
|---|---|---|
| пачками | ~65 | ~30 500 |
| пачками и сериями | ~17 | ~1250 |

Строк стало примерно в 24 раза меньше. Оставшиеся - датчики, которые за минуту набрали пять показаний подряд выше порога и встали на уровень 1. Обратно они не опускаются, поэтому в следующую минуту новых строк почти нет. Отставание тоже упало: смен уровня почти не стало, писать нечего.

### Шаг 7. Несколько экземпляров detectorа

Detector можно запускать в нескольких экземплярах в группе `threshold-detector`. Уровни датчиков он держит в памяти, а при ребалансировке партиция переходит к другому экземпляру. Чтобы тот не писал алерты по устаревшим уровням, слушатель ребалансировки (`ConsumerRebalancer` в `detector/consumer.py`) при получении партиций загружает состояния датчиков из базы. Датчики партиций, которые остались у экземпляра, сохраняют уровень и счетчик серии из памяти.

### Шаг 8. Вся система на одной машине

Прогоны по минуте, один detector. CPU - по `docker stats` во время прогона, в процентах одного потока.

| RPS | Шум у порога | Воркеров receiver | Отказы k6 | p95 | LAG | CPU receiver | CPU detector | CPU Kafka |
|---|---|---|---|---|---|---|---|---|
| 2750 | да | 1 | 0% | 38 мс | 202 | 82% | 55% | 44% |
| 3000 | да | 1 | 11,4% | 1 с | 102 | 100% | 32% | 25% |
| 8000 | нет | 8 | 0,09% | 157 мс | 354 | 416% | 57% | 53% |
| 8000 | да | 8 | 0-0,01% | 168-192 мс | 427-2200 | 411% | 65% | 40% |
| 10 000 | нет | 8 | 92% | - | - | - | - | - |

Один воркер receiverа держит 2750, на 3000 уже нет. Предел системы на моей машине - 8000 показаний в секунду. На 10 000 ломается генератор нагрузки: k6 исчерпывает свободные порты, а receiver почти простаивает. Больше всех процессора берет receiver, 4-5 потоков на 8000 показаний в секунду. Один detector держит 8000 показаний в секунду с шумом у порога и занимает меньше одного потока.

Отдельно я проверил скорость, с которой detector догоняет поток. Во время прогона на 6000 показаний в секунду я остановил его примерно на 16 секунд и запустил снова, снимая `LAG` командой из раздела "Запуск". К запуску накопилось ~100 000 сообщений, через 5 секунд после запуска `LAG` упал почти до нуля. За эти 5 секунд detector обработал накопленное и все, что пришло за это время, то есть не меньше 20 000 показаний в секунду, считая вступление в группу и загрузку состояний из базы.
